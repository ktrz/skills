# Changelog

## 0.2.0

- **Diff/delta overlay.** Diagram elements and components gain an optional `status: added | removed | changed | unchanged`, so a walkthrough can say what the PR did to a thing instead of only drawing the after picture. Supported on `lane` box cells, `lane` arrow cells, `sequence` actors, `sequence` steps, `depmap` nodes, `depmap` edges, and `components[]`. The field is optional at every one of those sites; an absent `status` claims nothing about the element and renders identically to `unchanged`. `render.mjs` picks the value up at every site: a border colour plus text badge on lane boxes, sequence actors, and components (lane/sequence `removed` additionally struck through), a border colour plus text badge on lane arrows (never struck through, even when `removed`) and status-coloured sequence steps, and stroke-colour-only on depmap nodes and edges so the character-count-driven layout geometry is never perturbed by a badge. A per-diagram legend renders below the diagram (outside the SVG, so a depmap's `viewBox` is unaffected) listing only the statuses actually present, in fixed enum order, and only when at least one is non-`unchanged`; `components[]` status gets a badge but no legend. The status is also appended to every element's aria-label/`<desc>` as a trailing `[status]` marker, omitted when `unchanged`. Every status consumer on a depmap reads the edges the renderer actually drew, not the raw edge list, so an edge whose endpoint fails to resolve contributes no arrowhead marker, no legend entry and no relationship text — such an edge is already rejected by `validate.mjs`, so this is defence-in-depth. So that a lane arrow can never advertise a status in the badge and legend that assistive tech cannot locate, an arrow lacking labelled boxes on both sides is now described in its own right (`Arrow → from Alpha: label [added]`) instead of being dropped from the flow list. +156 tests.
- **Base-sha receipts.** Receipts gain a `code-base` kind, a sibling of `code`/`doc`/`url`/`report` rather than a variant of `code`: same `path:line`/`path:line-line` ref shape, but resolving against a new document-level `baseSha` field (the PR's effective base — the merge base of the head and the base branch, pinned in Step 1 — not the base branch tip) instead of the head `sha`. This lets a claim about code the PR deleted still ground itself in evidence — that code no longer exists at the head sha, so a `code` receipt can't resolve it. `baseSha` is optional, required only when the document carries at least one `code-base` receipt; documents with none are unaffected. +33 tests, including one locking the renderer's unlinked-badge fallback for a `code-base` receipt on a document with no `baseSha` — a shape `validate.mjs` already rejects, so the test is defence-in-depth against a `blob/undefined/` URL rather than coverage of valid input. Step 7's pre-publish base-pin revalidation is unconditional, not gated on whether the document serializes `baseSha`: every `status` field derives from Step 2's diff against the effective base regardless of receipt kinds present, so the check now always re-derives the merge base and compares it against the effective base pinned in Step 1 — a base branch tip that moved without moving the merge base is not a mismatch. Both the Step 1 pin and the Step 7 revalidation name the base remote explicitly and fully qualify the ref — `git fetch <base remote> 'refs/heads/<baseRefName>'` rather than a hardcoded `origin` and a bare branch name, since `origin` is the head repo when the checkout is a clone of a fork and would pull a stale same-named branch, a bare name loses to a same-named tag, and the quotes keep shell metacharacters in a branch name inert. Both sites also spell out how the substitution has to be done: `baseRefName` goes in as one single-quoted shell word with every literal `'` rewritten as `'\''`, since `;`, `$(...)` and a literal quote are all legal in a branch name and the quote alone escapes the quoting — take `baseRefName` from the same `gh pr view` call that supplies the sha pins (Step 7 re-reads it, since retargeting a PR moves the base branch and the merge base together), and STOP when `git merge-base` can't resolve the base commit rather than guessing a base. A retarget that lands on the same merge base is not a mismatch either — the diff and the `code-base` receipts still resolve there, and nothing else is anchored to the base (`code` resolves at the head sha, `doc` at the PR's files page, `url` and `report` at no commit at all) — only the `pr.base` label goes stale, so Step 7 now says to correct `pr.base` from the re-read `baseRefName`, re-run validate + render, and publish with a label noting the retarget instead of stopping.
- **Status grounded in diff evidence.** `status` is no longer a model guess: the scout step now takes its file list from `git diff --name-status --no-renames <effective base>..HEAD` rather than `gh pr diff --name-only`, so every changed path carries its `A`/`M`/`D` diff marker through partitioning into research scopes. Two dots against the effective base pinned in Step 1, not three against the base branch tip: the two forms produce byte-identical listings, but only the two-dot form makes that pin load-bearing at the one site the base-commit bug came from, and the surrounding prose now warns against "simplifying" it to a two-dot diff against the tip, which would fabricate entries for base-side commits the PR never made. Both the research brief and the edge-verification brief now receive that same effective base sha, so deleted files can be read at the commit the PR actually diverged from (`git show <effective base>:<file>`) for real line numbers backing `code-base` receipts. The edge-verification brief's EDGES grammar gained a second bracketed token carrying each edge's diff status, derived from comparing the edge at base and at head, and omitted altogether for an edge the pass could not check at both commits — an omitted token leaves that edge with no `status` at all, which claims nothing about the edge and renders exactly as `unchanged` does. Synthesis guidance now spells out where each element family's status comes from — components roll up from the file-level `A`/`M`/`D` markers of all their files, not just the diff-listed ones, falling back to `changed` where the component's full file set can't be established (`added` and `removed` quantify over the whole set, and the diff listing alone never establishes it), depmap edges come from the edge-verification status token, depmap nodes derive from the file-level markers of the files they cover (coarsening to the matching component's status exactly when node and component cover the same files), and lane/sequence elements derive from the diff evidence for the code they represent, rolled up over that code's files with the same every/any/else arithmetic a component uses, and take no status at all when the element draws no file of this repo (a `phase` divider, an actor standing for a browser or a third-party service) — and that a status is always derived, never invented. Hardened after a live end-to-end run against a real PR: `stats.files` is now stated to come from the git listing rather than `gh pr view`'s `changedFiles`, which can legitimately differ by the rename count under `--no-renames`; the `A`/`M`/`D` to `added`/`changed`/`removed` mapping is spelled out outright, since the enum word is `changed` where git says "modified"; the `added` gloss no longer implies lineage it can't know, since it's a claim about paths and a renamed component can correctly read `added` at its new path and `removed` at its old one; and the edge-verification brief's Section A grammar was tightened — edges only, one line per source→target pair, both brackets spelled exactly, status describing the whole edge rather than individual symbols — with omitting the status token now framed as a correct, expected outcome and backed by a worked one-bracket example. Section A also now says what to do about paths and its own delimiters: nothing re-parses a path and the brackets are read only as the trailing one or two tokens, so a path that merely contains brackets (`app/[slug]/page.tsx`, an ordinary dynamic route) is written out in full, while a path that collides with the delimiters themselves — one embedding the arrow or colon-space separator, or ending in a bracketed token spelled like `[runtime]` or `[added]` — gets no edge line at all and is reported under SURPRISES instead, since the flat grammar has no escape for it — and because that routing can push an unbounded number of paths into SURPRISES, its five-bullet cap now exempts them by name, so every delimiter-colliding path is listed there however many there are. The template's code fence is now tagged `text`. The research brief now also spells out what a scoped subagent should do with a marker outside `A`/`M`/`D`: it has already been normalized to `M` upstream, and one reaching the subagent unnormalized is still `M`/`changed` to report, never a reason to drop the file. `references/schema.md`'s status-derivation section names that normalization too, so its component roll-up rule can't be read — by someone consulting that section alone — as an `A`/`M`/`D` vocabulary with no answer for a marker like `T`. The node minted for a cross-network edge target now has its `id` specified alongside its label, zone and absent `pkg`: a raw endpoint string is not a legal node id under `references/schema.md`'s rule 2, so the endpoint's distinguishing part is slugged into a readable `node.<slug>` (`node.stripe-charges` for `https://api.stripe.com/v1/charges`) with the exact string kept in `label`, a slug that collides with any id already in `nodes[]` — another endpoint's or a component's, since both share the `node.` namespace — is lengthened until they differ rather than merged, numerically suffixed, or quietly retargeted at the same-named component node, and the far-side zone the node names must be declared in the diagram's `zones[]` or rule 9 rejects the node. The brief now also pins what the first bracket describes: the classification is the edge as it stands at head — `[type-only]` only where every mechanism on the line is erased at build time, a `removed` edge classified as it stood at base for want of a head to describe, a flipped classification carrying head's token alone with the base state noted in the label, and a mixed pair (a type import beside a runtime one between the same two files) resolving to `[runtime]`, since one mechanism surviving compilation makes the dependency real. The status token's `changed` clause now covers the mechanism carrying an edge and not only what is imported or called, so a classification flip is a mechanism change and lands on `changed` instead of falling between the two clauses with no rule: `import type` at base against a runtime import at head is a `[runtime]` edge whose status is `changed` even though the symbol never moved, and the reverse — the `import`-to-`import type` severing that breaks a cycle or drops a bundle edge — is `[type-only]` and `changed` too, where the old wording invited the `unchanged` that would have hidden the PR's headline change. Synthesis maps that bracket onto the required `edges[].kind`, which the depmap step previously left the model to guess: `type-only` for a `[type-only]` line, `net` where the target is one of those minted endpoint nodes rather than a component in this repo, and `call` otherwise — target shape outranking mechanism, with `kind` staying an axis of its own rather than a restatement of `status`.
- **Untrusted diff listing neutralized before it is fenced.** The PR-controlled annotated file listing is now neutralized against fence-closing sequences before Step 2 wraps it in its `<external_data>` fence for subagent prompts: `<`, `>` and `/` are all legal in path components, so a repo can carry a path containing a literal `</external_data>` (or a forged opening tag) that would end the fence mid-listing and spill every later path outside the trust boundary. Step 2 now cites `references/prompt-injection-defense.md#fence-it` — the neutralize-inner-closing-tags rule — alongside the detect-flag scan it already ran. Step 4 now does the same for the aggregated component inventory it builds from the fan-out research reports before that inventory fills `references/edge-verification-brief.md`'s own `<external_data>` fence: the inventory carries the same report-derived, PR-controlled paths and symbol prose, so it poses the same fence-closing risk Step 2's listing did, and Step 4 had been interpolating it unneutralized. The same listing is also now documented as arriving C-quoted: the scout command gained `-c core.quotePath=false` so the common non-ASCII filename comes through as raw UTF-8 rather than as octal escapes like `"\303\274n\303\257cod\303\251.txt"` that no later `git show` can resolve, with the caveat spelled out that the flag does not disable quoting — git C-quotes control characters regardless, which is exactly what keeps the listing one record per line. Both fan-out briefs now tell the subagent to dequote before it shell-quotes: strip the surrounding double quotes and decode git's full C-style escape set — `\a`, `\b`, `\f`, `\n`, `\r`, `\t`, `\v`, `\"`, `\\`, and `\NNN` octal for any other byte — back to raw bytes before building a `git show` command, and fall back to the existing skip-and-report escape hatch when the decoding isn't certain. That hatch now fires only on what's left after decoding: a control character still present in the path (the surrounding double quotes are the tell, and `core.quotePath=false` again noted not to suppress them), an escape the subagent cannot decode with certainty, or a rewrite it is unsure of — not on a quote, backslash, or backtick by themselves, since the `'` → `'\''` rewrite already keeps those, and every other shell metacharacter, literal inside the quoting; treating their mere presence as a skip trigger made the documented `src/O'Neill.ts` example unreachable and discarded valid evidence. Section C's five-bullet cap now exempts every path a subagent skips instead of only the delimiter-colliding ones it already named: a skip earns its aggressiveness by being reported, and a PR touching many apostrophe-bearing paths would otherwise have had its skips truncated away by the cap. The component roll-up's confirm-the-whole-file-set listing is now quoted, flagged, and pathspec-literal — `git -c core.quotePath=false ls-files -- ':(literal)<dir>'`, with `<dir>` substituted as a single-quoted shell word and the listing skipped when the directory name can't be quoted with certainty: `<dir>` traces back to the same PR-controlled diff paths and `--` stops only option injection, not shell, so a directory named `src/a$(id -un)b` ran the subshell under the old unquoted form. Shell quoting alone doesn't stop git itself from reading the pathspec as magic, since git parses `*`, `?`, `[`, and a leading `:` after the shell is done: an unescaped `'src/a[bc]d'` also matches the unrelated sibling `src/abd`, and a directory name starting with `:` reads as the start of a magic signature instead of a literal colon, both padding the very file set `added`/`removed` quantify over; `:(literal)` turns that matching off without narrowing what the pathspec covers. And the flag is what makes these paths comparable byte for byte against Step 2's listing, which otherwise renders a non-ASCII path C-quoted on one side and raw on the other, silently missing the file and downgrading an `added` component to `changed`.

## 0.1.0 - 2026-07-13

Initial release: a `/narrate-pr` skill that turns a PR into a validated, self-contained HTML walkthrough. Feature-complete and tested, but not yet hardened through repeated real-world use — staying pre-1.0 until it's proven in action.

- **Input contract** — `walkthrough.json` v1 schema (`references/schema.md`) with a zero-dependency validator: 16 rules with all-violations reporting, covering receipt ref shapes (doc/url/report), repo-relative code refs with positive line numbers (Windows drive-letter and backslash paths rejected), depmap layout bounds, a node-to-layout bijection so no node goes undrawn, required prefixed ids, review-order step contiguity, and structure violations for non-object collection entries.
- **Renderer** — deterministic `render.mjs` (byte-identical HTML per input, zero deps): lane, sequence, and depmap diagrams; a generated per-package palette; dual light/dark themes; sha-pinned code receipts and PR-diff-anchored doc receipts; a `--standalone` flag; and a golden fixture. Every href is scheme-allowlisted (`javascript:`/`data:` rejected) and blob-URL path segments are percent-encoded (spaces/`#`/non-ASCII) while the diff-anchor digest stays on the raw path. Report receipts render as local-only badges in fragment mode, with `--report-map` mapping them to published artifact URLs. Depmap-only architecture emits no empty Architecture section or dead TOC link. The CLI rejects a second positional path (exit 2) rather than silently rendering the last.
- **Inline markdown** — a safe subset (code spans, links, emphasis) rendered from pre-escaped text with no raw-HTML passthrough. Links are stashed before the emphasis pass (URLs with `_`/`*` survive intact), link sentinels restore before code sentinels (inline code inside link text is preserved), and any sentinel character in user input is entity-encoded so it cannot forge a placeholder. Placeholders are pure-ASCII, keeping `render.mjs` a text blob.
- **Depmap layout** — exemplar label grammar (no tag backgrounds, wrapped/beside-the-line labels), label-width-aware gutter/row sizing, border-anchored perpendicular edge stubs, gutter-centerline routing (no through-node or collinear legs), and chips that wrap inside node rects. Refined after live acceptance feedback.
- **Skill workflow** — full `SKILL.md` pipeline (scout -> fan-out research -> edge verification -> synthesize -> validate/render -> artifact publish) with a trust-boundaries table: a dirty-tree checkout guard, PR identity fetch (`pr.repo`/`pr.branch`/`pr.base`), a fenced-and-scanned file list, `<external_data>`-fenced fan-out payloads, a PR-payload budget (title+body <= 20 KB, file list <= 2000 entries), explicit `<output-dir>` paths, and `disable-model-invocation: true` so the skill only triggers via `/narrate-pr`.
- Acceptance-tested end-to-end on a real 112-file PR; `node --test` suite of 77 tests; version gate passed by Chris 2026-07-13.
