## 1.11.0

- Day-plan issue lookups now define what happens when a title search returns several same-date issues. The daily flow creates a fresh `<TODAY> — …` issue and closes the previous one, so a second run on the same day deterministically leaves two same-date issues (one closed, one open) — and no lookup said which to use. All three now filter on the exact `<TODAY> — ` title prefix first (`--search` matches loosely and returns near-misses), then resolve deterministically. `references/close-day.md` C0 uses the single `OPEN` match when several exist (the expected shape after a repeat run), takes the highest-numbered when none are open and falls through to the existing already-closed refusal, and hard-stops with an ambiguity error listing the issue numbers when more than one is open; previously it could select the closed sibling and report "already closed, nothing to do" while the live plan went untouched. `references/standup.md` S0 keeps `--state open`, so closed siblings are invisible and any multi-match is necessarily multiple open plans — it hard-stops in that case, and the file now documents why it keeps `--state open` where close-day uses `--state all`. `references/monthly-review.md` M1 preserves its exact-title match and, on multiple open matches, emits a warning listing the issue numbers, leaves `MONTHLY_REVIEW_NUMBER` unset and returns without creating a duplicate, so the daily brief degrades to skipping the posture hint rather than blocking the run; the "never edit the body, never reopen a closed retro" guarantee now covers every returning branch. Deliberately out of scope: the daily flow still has no create-time idempotency guard, so same-date duplicates can still be created — these fixes make the lookups handle that state safely rather than prevent it.
- Done-label matching is now genuinely symmetric. `DONE_LABELS` entries are trimmed of surrounding whitespace on insertion, matching the already-documented trimmed, case-insensitive comparison. Previously insertion was verbatim while lookup was trimmed, so a padded label never matched and its Plan-section checkbox never flipped.
- Ticket-ID patterns de-duplicated. `SKILL.md` (the `git worktree list` branch-name parsing site) and `references/close-day.md` (the `### Done` block parsing site) no longer restate the ticket regexes; both defer to `references/tracker.md` → **Ticket ID format**, the single source of truth. The restatements were also wrong: the ClickUp pattern had no token boundaries at all, so it matched inside longer tokens, and the GitHub and jira/linear patterns were looser than canonical — `SKILL.md`'s restatement even contradicted its own upstream `TICKET_ID_REGEX` definition.
- Synced `references/tracker.md`: ticket-ID patterns now have a single source of truth, the GitHub branch-name fallback requires an explicit `#<n>` rather than accepting a bare number, the ClickUp matcher's token boundaries exclude uppercase, and the default-branch snippet resolves the discovered name to a revision the clone actually has (`refs/heads/<b>` → `origin/<b>` → skip) instead of assuming a local branch exists.
- Synced `references/prompt-injection-defense.md` — wording only, no normative change: the re-fencing rule's example now names any verbatim external payload (comment body, issue or ticket description, Slack message, fetched web page) rather than only a comment body.
- CodeRabbit review fixes: `date` calls used for day-plan windows now fall back to GNU `date -d` when BSD `date -j`/`-v` isn't available, so Phase 1/setup works on macOS and Linux; the tracker-search JQL drops the rolling `-7d` window in favour of `statusCategory != Done` so older untouched tickets stay visible; the GitHub ticket-extraction rule prefers the first 3+ digit run when multiple numbers appear (matching `references/tracker.md`); the done-label match is now an exact (trimmed, case-insensitive) match instead of substring containment, so `Review PR #1` can no longer flip `Review PR #10`; `close` now queries issues with `--state all` (not just `open`) and refuses cleanly with a "already closed" message instead of re-running C1–C4 against an already-closed issue; issue create/edit now write the body to a temp file and pass `--body-file` instead of inlining `--body`; the monthly-review previous-month date fallback anchors to the first of the current month before subtracting so it no longer overflows on 31-day months.
- Synced `references/tracker.md` again: the generic fallback steps (recent-commit scan, then ask the user) are now explicitly scoped to jira/linear/clickup, and to github only when no PR exists yet — the `github` bullet's own fallback (PR title, else ask the user) is terminal, so a reading agent can no longer fall through a deliberate "ask the user" into a multi-commit scan where an unrelated `#<n>` in older history could win.
- `references/standup.md` Phase S0's `gh issue list` now adds `--search "in:title \"<TODAY> —\""` alongside the existing `--state open --limit 10`, so today's day-plan issue can't fall outside the newest-10 window and produce a false "No match" on a busy repo — matching the pattern `references/close-day.md` already uses.
- `DAYS_SINCE` now derives `TODAY_TS` by parsing `$TODAY` the same date-only way as `LAST_PLAN_TS`, and subtracts the two date-only timestamps, instead of subtracting `LAST_PLAN_TS` from the live `date +%s`. On GNU, `date -d "<date-only>"` defaults to midnight, so the old form made the day count depend on what time of day the skill ran.

## 1.10.0

- Suppress already-actioned review asks. Phase 3 gains a "Resolve review state for referenced PRs" sub-step: after Slack dedup, fenced message bodies are scanned for PR references (`github.com/<owner>/<repo>/pull/<N>` URLs, plus `#N` only with repo context), mapped to `(repo, N, message_ts)`, and review state for those PRs plus all `reviewRequested` PRs is fetched in one `gh api graphql` batch (`state`, `headRefOid`, `reviews(last: 20) { author { login }, state, submittedAt, commit { oid } }`, `viewer { login }` → `ME_LOGIN`) — no new `allowedTools` entry needed. Phase 4 gains a state-aware suppression rule keyed on whether my latest review covers the PR's current head, not on ask timing: a "Review PR #N" bullet is dropped when the PR is merged/closed, or when my latest review is `APPROVED` **and** GitHub is not actively re-requesting my review (`reviewRequested_repoI` records are tagged `isReviewRequested` and take precedence over the approval drop, so a fresh re-request after an approval still renders); kept in "Do first" when my latest review is `CHANGES_REQUESTED` and the head SHA moved since it (author pushed); moved to a quiet "Already handled" sub-note when my review's `commit.oid` matches `headRefOid` or was only `COMMENTED`; anything uncertain (no review, lookup error) stays in "Do first". Freshness is decided by commit-SHA equality (`review.commit.oid` vs `headRefOid`), not timestamps, so a preserved-date rebase can't make a stale PR read as handled. `message_ts` is now cosmetic (note wording only), so multiple Slack mentions of the same PR no longer risk suppressing the wrong bullet. Trust boundaries table gains a row for review author logins, states + commit SHAs (structured, compared not quoted, LOW).
